# Контур — сценарное планирование в розничной торговле

Проект ВКР Королева Дмитрия Геннадиевича. Локальное приложение связывает
реальные продажи, прогнозирование, пополнение запасов и сравнение сценариев.
Backend — Flask, frontend — HTML/CSS/JavaScript, база — SQLite.

## Запуск

Нужен Python 3.12 или новее. В текущем проекте библиотеки установлены в `.venv`.
В терминале PyCharm из папки проекта:

```bash
source .venv/bin/activate
python main.py
```

Откройте http://127.0.0.1:5050. Остановка сервера — `Ctrl+C` в терминале.
Другой порт: `python main.py --port 5051`.
В PyCharm можно выбрать интерпретатор `.venv/bin/python` и запустить `main.py`.

После клонирования репозитория (команда `python3` должна означать Python 3.12+):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

Первый запуск создаёт `data/project.sqlite3` и импортирует существующий CSV M5.
Исходные продажи не изменяются. При следующих запусках используются сохранённые
данные и исследования. Интернет, внешние API и CDN приложению не нужны.
Это локальный однопользовательский режим с выключенным отладчиком и привязкой
к `127.0.0.1`; публичный многопользовательский сервер в эту версию не входит.

## Как пройти весь процесс

1. **Данные.** Выберите встроенный M5 или загрузите свой CSV. Проверьте период,
   валюту, число товаров и первые строки. При ошибке набор не сохраняется.
2. **Прогноз.** Задайте название исследования, модель и горизонт 7–56 дней.
   Приложение сохраняет будущий прогноз, качество на истории и допущения.
   Будущий календарь можно передать в форме как CSV `date,snap,event`.
3. **Проверка качества.** Переключайте будущий график и проверку на истории.
   Метрики доступны по товарам на последнем окне и по всем трём окнам вместе.
4. **Сценарии.** Базовый вариант создаётся автоматически. Добавьте рост спроса,
   задержку поставки, новую цену, промо или другую политику пополнения.
   Для редактирования базового варианта сначала создайте его копию.
5. **Сравнение.** Отметьте 2–8 вариантов. Смотрите финансовый результат, продажи,
   дефицит, конечный запас, товар в пути и уровень обслуживания.
6. **Подробности.** Откройте дневное движение товара и проверьте чувствительность
   к изменению спроса. CSV можно скачать кнопками; экспорт сравнения содержит
   именно показанные варианты.
7. **История.** Откройте сохранённое исследование после перезапуска приложения.
   Прогноз и параметры останутся теми, которые были сохранены при расчёте.

Продуктовые вопросы: хватит ли запаса при росте продаж; что изменится при
задержке поставщика; какой остаток создаёт выбранная политика; оправдана ли
скидка при заданной реакции покупателей; насколько результат устойчив к спросу.
Система показывает последствия и не выбирает решение за пользователя.

## Что означают расчёты

В основе — реальные данные Walmart M5: три товара магазина `CA_1`,
5823 наблюдения за 29.01.2011–22.05.2016. Подробности источника и преобразований:
[data/README.md](data/README.md). Собственный CSV использует тот же формат.

История содержит наблюдаемые продажи. Для сценарного расчёта прогноз этих
продаж принимается как ожидаемый спрос. Потерянный спрос не восстановлен.
Начальный запас, себестоимость, поставки, ценовая эластичность и промоэффект
задаются пользователем, поскольку этих сведений в M5 недостаточно.
**Финансовый результат является модельным, а не фактической прибылью магазина.**

Базовый будущий прогноз начинается на следующий день после конца истории.
Цена фиксируется на последнем наблюдаемом уровне. Без отдельного календаря
будущие SNAP и события равны 0 — это явно указанное допущение. Если календарь
задан, его значения сохраняются со снимком исследования.

Три модели: среднее последних 7 дней, повторение последней недели и Ridge.
Для всех применяется одинаковая проверка: до трёх непересекающихся окон
длиной в выбранный горизонт. В каждом окне обучение предшествует проверке,
будущая цена равна последней цене обучения, лаги рекурсивно заполняются прогнозами.
Календарь исторического проверочного периода считается заранее известным.

При горизонте 28 дней общая WAPE на трёх окнах составляет 21,17% для Ridge,
25,85% для сезонного наивного метода и 29,82% для среднего. На последнем окне:
18,90%, 25,06% и 26,53% соответственно. Эти результаты относятся к данной
выборке; они не являются официальным результатом соревнования M5.

Сценарный спрос учитывает внешнее изменение, степень изменения цены при заданной
эластичности и дополнительный промоэффект. Начальный запас считается по базовому
прогнозу, поэтому рост спроса сам по себе не увеличивает исходный остаток.
Порядок дня: поступление → пересмотр заказа → продажи → хранение остатка.
Заказ учитывает товар в пути. Неудовлетворённый спрос теряется, обратных заказов нет.
Ранее размещённые заказы на начало горизонта не заданы; начальный pipeline равен 0.

Финансовый результат = выручка − себестоимость проданного − хранение −
оформление заказов − промобюджет. Стоимость всех размещённых заказов, включая
товар в пути, показывается отдельно и не вычитается повторно.
Налоги и постоянные расходы не включены. Дробные единицы обозначают ожидаемые
объёмы: упаковки, списания по сроку годности и неопределённые сроки не моделируются.

## Структура без дополнительных уровней вложенности

```text
Diplom/
  main.py                   общий запуск веб-приложения
  requirements.txt          зависимости
  chapter1/                 первоначальный анализ и три простых модели
  chapter2/                 сценарный расчёт, его тесты и вторая глава
```

Порядок чтения: `main.py` → `common/main.py` → `chapter3/app.py` →
`chapter3/service.py` → `common/database.py`, `common/forecasting.py`,
`chapter2/scenarios.py`. Исследовательский анализ первой главы отдельно:

```bash
python -m chapter1.main
python -m chapter1.main --plots
```

## Где улучшать ML

`common/forecasting.py:predict_model(train, plan, model)` — единая точка
вызова модели для будущего прогноза и всех временных проверок. Функция возвращает
одномерный числовой массив по датам плана. История содержит только прошлые
продажи, план — даты, цену и календарные признаки.

Для замены внутреннего алгоритма Ridge измените соответствующую ветку этой
функции и обновите `version` в `MODELS`. Формат прогноза сохраняется:
`date, sku, prediction, price`. Сценарии, SQLite и API сохранят свой контракт.
Версия модели записывается с исследованием; старые результаты не пересчитываются.
Если добавляете метод с новым именем, добавьте его также в список моделей UI.

## База данных и API

`datasets` хранит описание, валюту и контрольную сумму набора; `sales` — дневные
продажи; `runs` — прогноз, версию модели, метрики, календарь и допущения;
`scenarios` — параметры и сводки; `scenario_daily` — дневные результаты.
Наборы и снимки исследований не изменяются. Удаление сценария удаляет его
дневные записи через внешний ключ. Транзакции предотвращают частичный импорт.
Повторный импорт одинакового набора в той же валюте возвращает существующую запись.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/datasets` | Сохранённые наборы |
| `POST /api/datasets` | Проверка и импорт CSV |
| `GET /api/datasets/<id>/preview` | Просмотр первых строк |
| `GET/POST /api/runs` | История и создание исследования |
| `GET /api/runs/<id>` | Снимок исследования с вариантами |
| `POST /api/runs/<id>/scenarios` | Новый вариант |
| `PUT/DELETE /api/scenarios/<id>` | Изменение и удаление варианта |
| `POST /api/runs/<id>/compare` | Сравнение выбранных вариантов |
| `POST /api/runs/<id>/sensitivity` | Чувствительность без записи в БД |
| `GET /api/runs/<id>/export` | CSV выбранного вида |

Ограничения прототипа: CSV до 10 МБ, 50 000 строк, 20 товаров, один магазин,
полный общий дневной календарь. Нужны минимум 56 обучающих дней и горизонт
проверки (для стандартных 28 дней — не менее 84 дней истории).
Записывающие запросы требуют CSRF-токен страницы. Ошибки API возвращаются в JSON.

## Проверки

```bash
python -m unittest discover -v
```

35 проверок: 6 для первоначальных моделей и данных; 11 для сценарного ядра;
18 для приложения и ML-адаптера. Проверяются балансы товара и стоимости,
отсутствие двойного списания закупок, учёт поставок в пути, изоляция сценариев,
атомарность загрузки, будущие признаки, единая модель для прогноза и проверки,
сохранение календаря и результатов после перезапуска, CSRF и CSV-экспорт.
Тесты используют временную SQLite-базу и не меняют пользовательские расчёты.

## Документы и GitHub

В папках глав находятся DOCX и краткие пояснения TXT для руководителя.
Первая глава описывает аналитический этап; актуальный общий запуск приведён выше.

PDF, локальную базу и её журналы, `.venv`, настройки IDE и временные файлы.
